# Планирование выездов инженеров — команда Трдельник

Кейс «Билайн Бизнес», хакатон «Лидеры цифровой трансформации» 2026. По заявкам дня и составу бригад строим план:
какая бригада какие заявки выполняет, в каком порядке и во сколько; перестраиваем его после событий в течение дня и
показываем диспетчеру на карте с объяснениями.

- **Демо без установки:** https://route-dispatcher-trdelnik.vercel.app
- Модель, алгоритм, точные методы и результаты — [docs/SOLUTION.md](docs/SOLUTION.md)
- Допущения и ответы жюри — [docs/assumptions.md](docs/assumptions.md), стенограмма вопросов и ответов — [docs/qa.txt](docs/qa.txt)
- Контракт с решателями на C++ — [docs/SOLVER_IO.md](docs/SOLVER_IO.md)
- Презентация — [presentation/presentation_trdelnik.pdf](presentation/presentation_trdelnik.pdf)

## Запуск одной командой

Нужен Docker.

```
docker compose up --build
```

Откройте http://localhost:8080. Контейнер собирает решатели, строит планы шести участков (Восток, Югоцентр,
Юго-восток, Север, Запад, Северо-восток), перестраивает план Востока после пяти событий и запускает страницу
диспетчера. Первый запуск — около 5 минут, дальше около минуты.

OSRM для демо не нужен: координаты, матрицы времени и расстояний и линии маршрутов по улицам лежат в `cache/`.
Браузеру нужен интернет: подложка карты OpenStreetMap, библиотека Leaflet и шрифты грузятся из сети. Для новых
адресов — см. «Новые адреса: геокодинг и OSRM».

## Без Docker

Нужны clang или g++, make, Python 3.11+.

```
make -C solver                                             # решатели: solver/bin/plan, baseline, fleet_bound
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
scripts/demo.sh                                            # то же, что контейнер; --no-serve — без запуска страницы
```

`scripts/demo.sh` пишет результаты в `out/<участок>/`, страницу — в `site/` и открывает её на порту `PORT`
(по умолчанию 8080). Юго-восток считается 10 секунд, остальные участки — 3.

## Сценарий демо (раздел 4 ТЗ)

| Шаг ТЗ | Где на странице |
|---|---|
| 1–2. Открыть данные, запустить планирование | `python -m dispatch plan …` (или `scripts/demo.sh`); на странице — выбор участка слева вверху |
| 3. Распределение и маршруты на карте | вкладка «План»: карта, бригады в работе, шкала дня |
| 4. Почему заявка назначена этой бригаде | клик по точке на карте или по блоку на шкале — карточка заявки с объяснением |
| 5–6. Событие и перестроенный план | вкладка «Изменения», список «Событие»: что изменилось, было / стало, новые участки маршрутов |
| 7. Сравнение с базовым вариантом | метрики вверху и блок «Сравнение с базовым вариантом ТЗ»: бригады, пробег по каждой бригаде и всего |

Готовые события Востока: авария в 11:30, отмена заявки в 13:00, новое подключение в 13:30, Бригада 4 недоступна
с 14:00, авария в 14:00. Любое другое событие — командой `replan` (ниже).

## Команды

Из корня проекта: `python -m dispatch <команда>` (в `.venv`: `.venv/bin/python -m dispatch …`).

| Команда | Что делает |
|---|---|
| `plan <заявки> -b <бригады> -o <папка>` | План на день: наш решатель, базовый вариант из ТЗ, нижняя граница числа бригад, проверка, причины неназначения и объяснения |
| `replan <папка плана> --at 14:00 <событие> -o <папка>` | Перестройка после события |
| `site <папки> -o site` | Страница диспетчера по результатам `plan` и `replan`: каждое событие привязывается к плану, от которого сделан `replan` |
| `serve [site] [--port 8080]` | Открыть страницу локально |
| `prefetch <папки плана>` | Линии по улицам для всех пар точек участка в кэш, чтобы показывать без OSRM |
| `demo-data [--transport mix1\|mix2\|pt\|car]` | Файлы бригад и заявок для демо по данным организаторов → `data/demo/` |
| `gen-district Север Запад Северо-восток [--seed 1]` | Новые участки Москвы с настоящими адресами из OpenStreetMap |
| `calibrate sample\|fit <файл> [-n 30] [--apikey …]` | Калибровка коэффициента пробок по Яндекс Картам |

Параметры `plan`:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `--name` | из имени файла | название участка |
| `--time` | 3 | время решателя, секунды |
| `--seed` | 1 | сид решателя |
| `--traffic` | `car=1.3` | множитель времени OSRM по видам транспорта |
| `--overhead` | `car=5,pt=3,bike=3,foot=3` | минуты на подход к заявке: парковка, дверь, домофон |
| `--no-geometry` | — | не строить линии маршрутов по улицам (быстрее, без OSRM и кэша линий) |

События `replan` (одно на запуск): `--unavailable "Бригада 4"` (имя или номер), `--cancel <номер заявки>` или
`--urgent "<адрес>"` / `--urgent "55.74, 37.72"` с `--type авария|подключение|ремонт|дозаказ` (по умолчанию авария),
`--window 15:00-17:00`, `--need авто`, `--id <номер>`, `--district <район>`. У аварии окно не нужно: она должна
начаться не позже чем через 2 часа.

```
python -m dispatch plan "data/demo/Восток заявки.xlsx" --name Восток -b "data/demo/Восток бригады.xlsx" -o out/Восток
python -m dispatch replan out/Восток --at 14:00 --urgent "55.74, 37.72" --type авария -o out/Восток_авария
python -m dispatch site out/Восток out/Восток_авария -o site
python -m dispatch serve
```

## Входные данные

Примеры — `data/demo/`. Исходные файлы организаторов — `data/organizers/`.

**Заявки** — CSV организаторов (CP1251 или UTF-8, разделитель «;») или xlsx с теми же колонками. Строка заголовка
начинается с «Заявка».

| Колонка | Значение |
|---|---|
| Заявка | номер |
| Тип заявки BK | `Подключение`, `Глобальная проблема` (авария), `Локальная заявка` (ремонт), `Дозаказ` |
| Тип заявки HD | подтип, только для показа (необязательная) |
| Начало, Окончание | окно начала работ: `17.08.2026 12:00` или `12:00` |
| Район, Адрес | адрес в формате организаторов |
| Транспорт | необязательная: требуемый транспорт — `авто`, `авто или велосипед`; пусто или `любой` — без ограничения |

Последняя строка — `Адрес офиса; <адрес>`: оттуда выезжают бригады без своего старта.

**Бригады** — xlsx или CSV: `Бригада; Транспорт; Навыки; Старт`. Транспорт — `авто`, `общ. транспорт`, `велосипед`,
`пешком`. Навыки через запятую — `ремонт`, `подключение` (подключение и дозаказ), `аварии`. Старт — пусто (офис),
адрес или `широта, долгота`.

**Справочники ТЗ (2.4.1) → наши значения.** Навыки: 1 «Локальные работы» → ремонт, 2 «Подключение и дозаказы» →
подключение, 3 «Аварийные работы» → аварии. Транспорт: 1 автомобиль → авто, 2 пешеход → пешком, 3 велосипед,
4 общественный транспорт. Приоритет задаётся типом заявки: авария → подключение → ремонт и дозаказ; срочная
заявка приходит событием `replan --urgent`.

**Нормативы и единицы.** Работа на месте: подключение 70 мин, авария 80, ремонт 30, дозаказ 20 (Нормативы.xlsx без
20 минут «дороги» — дорогу считаем по картам). Смена у всех бригад 10:00–22:00: работа должна начаться внутри окна
и закончиться до 22:00; приехать раньше и ждать можно. Время — ЧЧ:ММ, длительности и время в пути — минуты,
расстояния — км, координаты — широта/долгота.

## Результат

`plan` пишет в папку результата:

| Файл | Что внутри |
|---|---|
| `plan.xlsx` | листы «Маршруты» (бригада, порядок, заявка, адрес, окно, приезд, начало, конец, км от предыдущей), «Бригады», «Метрики», «Неназначенные» с причиной, «Объяснения», «Базовый вариант», «Базовый — неназначенные»; после `replan` ещё «Изменения» |
| `plan.json` | всё то же для страницы: заявки, бригады, маршруты с временем и км, метрики, проверка, причины, объяснения, базовый вариант, нижняя граница; после `replan` — событие и список изменений |
| `task.txt`, `answer.json` | задача и ответ решателя — их можно проверить независимо (формат — `docs/SOLVER_IO.md`) |

Метрики из ТЗ: число задействованных бригад, пробег по каждой бригаде и суммарный — у нашего плана и у базового
варианта. Каждый план проходит отдельную проверку всех ограничений (`dispatch/planning/validate.py`): навык,
окно, конец смены, требуемый транспорт, каждая заявка назначена не больше одного раза.

## Как считаем

- **Цель по порядку важности:** выполнить все заявки (если нельзя — сначала аварии, затем подключения, затем
  остальные), затем меньше бригад, затем меньше километров.
- **Время в пути:** OSRM по дорогам OpenStreetMap; машина × 1,3 (пробки, сверено по Яндекс Картам) + 5 мин на
  подход, остальные + 3 мин. Общественный транспорт: до 1,5 км пешком, дальше 12 мин на подход и ожидание и
  20 км/ч, после 25 км — 45 км/ч.
- **Решатель** (`solver/plan`, C++): 8 потоков с разными эвристиками (имитация отжига, ALNS, SISR) обмениваются
  лучшим планом. **Базовый вариант** (`solver/baseline`) — ровно правило раздела 2.3 ТЗ. **Нижняя граница**
  (`solver/fleet_bound`) — генерация столбцов: доказывает, меньше какого числа бригад нельзя.
- **Результаты:** на 88 тестовых задачах план во всех выходит на доказанный минимум бригад; у базового варианта
  бригад на 41% больше и 22% заявок не выполнено. Подробно — [docs/SOLUTION.md](docs/SOLUTION.md), раздел 6.

### Правила перепланирования

Выполненное и начатое к моменту события не меняется. Новая обычная заявка встаёт в свободный промежуток, порядок
остальных не меняется. Авария, появившаяся в течение дня, начинается как можно раньше и не позже чем через 2 часа:
в цене каждая минута ожидания аварии, каждый перенос заявки и вывод резервной бригады. Заявки недоступного инженера
переходят к другим бригадам, затем к резерву. Отмена освобождает время для неназначенных заявок.

## Новые адреса: геокодинг и OSRM

Новые адреса переводятся в координаты через Nominatim (нужен интернет, не чаще раза в секунду) и сохраняются в
`cache/geocode.json`. Время и расстояние для новых точек даёт только свой OSRM:

```
osrm/download.sh                        # готовые графы из релиза GitHub: 1,2 ГБ, распакованные ~3 ГБ
docker compose --profile osrm up        # приложение и три сервера OSRM
```

`download.sh` качает через `gh`, пока репозиторий приватный (нужен `gh auth login` с доступом к нему), иначе через
`curl`. Собрать графы самим из OpenStreetMap: `osrm/build.sh` (Docker, ~8 ГБ памяти, 15–30 минут).

Без Compose: `docker run -d --name osrm-car -p 5003:5000 -v $PWD/osrm/car:/data osrm/osrm-backend osrm-routed
--algorithm mld --max-table-size 2000 /data/msk.osrm`, так же `osrm-bike` (порт 5002, папка `bicycle`) и `osrm-foot`
(5001, `foot`).

## Тесты

```
.venv/bin/python -m pytest                 # всё, ~15 с
.venv/bin/python -m pytest -m "not e2e"    # только модульные, без решателей
```

Модульные — на маленьких задачах «на прямой», где расписание считается в уме. Сквозные (`tests/e2e/`) запускают
настоящие решатели на демо-данных Востока без OSRM: план, отчёт xlsx, события, страницу, сообщение об ошибке во
входном файле, контракт с решателями. Им нужны
собранные решатели (`make -C solver`) и кэши в `cache/`.

## Ограничения и что дальше

- Смена у всех бригад одна, 10:00–22:00, без перерывов; от неё во многом зависит экономия бригад.
- Общественный транспорт — по средней скорости, без расписаний; пробки — один коэффициент на весь день.
- События задаются командой `replan`, а на странице выбираются из готовых; добавление события прямо со страницы и
  ручное переназначение с проверкой — следующий шаг.
- Строгий порядок «сначала бригады, потом км» иногда даёт дорогой размен (одна бригада против сотни км); цену
  бригады в км стоит сделать настройкой диспетчера.
- Дальше: пробки по часам, расписания транспорта, обеды и разные смены, планирование на несколько дней.

Подробно — [docs/SOLUTION.md](docs/SOLUTION.md), раздел 8.
