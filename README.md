# Планирование выездов инженеров — команда Трдельник

Кейс «Билайн Бизнес», хакатон «Лидеры цифровой трансформации» 2026. По заявкам дня и составу бригад строим план:
какая бригада какие заявки выполняет, в каком порядке и во сколько; перестраиваем его после событий в течение дня и
показываем диспетчеру на карте с объяснениями.

Модель, алгоритм, точные методы и результаты — [docs/SOLUTION.md](docs/SOLUTION.md), допущения и ответы жюри —
[docs/assumptions.md](docs/assumptions.md).

**Демо без установки:** https://lct-trdelnik.vercel.app — та же страница диспетчера, что собирает `scripts/demo.sh`
(папка `site/`). Обновить после пересборки: `cd site && vercel deploy --prod` (проект `lct-trdelnik`; если папка
пересоздана, сначала `vercel link --project lct-trdelnik`).

## Запуск одной командой

```
docker compose up --build
```

Откройте http://localhost:8080. Контейнер собирает решатели, строит планы шести участков, перестраивает план Востока
после пяти событий и запускает страницу диспетчера. Первый запуск — около 5 минут, дальше около минуты.

OSRM для демо не нужен: координаты, матрицы времени и расстояний и линии маршрутов по улицам лежат в `cache/`.
Для новых адресов нужен свой OSRM — см. ниже.

## Без Docker

Нужны clang или g++, make и Python 3.11+.

```
make -C solver
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
scripts/demo.sh                        # то же, что делает контейнер
.venv/bin/python -m pytest             # тесты: модульные и сквозные
```

## Команды

Из корня проекта: `python -m dispatch <команда>` (в `.venv`: `.venv/bin/python -m dispatch ...`).

| Команда | Что делает |
|---|---|
| `plan <заявки> -b <бригады> -o <папка>` | План на день: наш решатель, базовый вариант из ТЗ, нижняя граница числа бригад, проверка, причины неназначения и объяснения. Пишет `plan.xlsx` и `plan.json` |
| `replan <папка плана> --at 14:00 <событие> -o <папка>` | Перестройка после события: `--unavailable "Бригада 4"`, `--cancel <номер>` или `--urgent "<адрес>" --type авария\|подключение\|ремонт\|дозаказ [--window 15:00-17:00] [--need авто]` |
| `site <папки> -o site` | Статическая страница диспетчера по результатам `plan` и `replan` |
| `serve [site]` | Открыть страницу локально, http://localhost:8080 |
| `prefetch <папки плана>` | Линии по улицам для всех пар точек участка в кэш, чтобы показывать без OSRM |
| `demo-data` | Файлы бригад и заявок для демо по данным организаторов → `data/demo/` |
| `gen-district Север Запад Северо-восток` | Новые участки Москвы с настоящими адресами из OpenStreetMap |
| `calibrate sample\|fit` | Калибровка коэффициента пробок по Яндекс Картам |

```
python -m dispatch plan "data/demo/Восток заявки.xlsx" --name Восток -b "data/demo/Восток бригады.xlsx" -o out/Восток
python -m dispatch replan out/Восток --at 14:00 --urgent "55.74, 37.72" --type авария -o out/Восток_авария
python -m dispatch site out/Восток out/Восток_авария -o site
python -m dispatch serve
```

### Входные файлы

- **Заявки** — CSV организаторов (CP1251 или UTF-8, разделитель «;») или xlsx с теми же колонками: Заявка; Тип заявки BK;
  Тип заявки HD; Начало; Окончание; Район; Адрес; необязательная колонка «Транспорт» («авто», «авто или велосипед»;
  пусто — любой). Последняя строка — «Адрес офиса; <адрес>».
- **Бригады** — xlsx или CSV: Бригада; Транспорт (авто, общ. транспорт, велосипед, пешком); Навыки (ремонт,
  подключение, аварии); Старт (пусто — офис, иначе адрес или «широта, долгота»).

### Правила перепланирования

Выполненное и начатое к моменту события не меняется. Новая обычная заявка встаёт в свободный промежуток, порядок
остальных не меняется. Авария, появившаяся в течение дня, начинается как можно раньше и не позже чем через 2 часа:
в цене каждая минута ожидания аварии, каждый перенос заявки и вывод резервной бригады. Заявки недоступного инженера
переходят к другим бригадам, затем к резерву. Отмена освобождает время для неназначенных заявок.

## Свой OSRM для новых адресов

```
osrm/download.sh                        # готовые графы из релиза GitHub: 1,2 ГБ, распакованные ~3 ГБ
docker compose --profile osrm up
```

`download.sh` качает через `gh`, пока репозиторий приватный (нужен `gh auth login` с доступом к нему), иначе через
`curl`. Собрать графы самим из OpenStreetMap: `osrm/build.sh` (Docker, ~8 ГБ памяти, 15–30 минут).

Без Compose: `docker run -d --name osrm-car -p 5003:5000 -v $PWD/osrm/car:/data osrm/osrm-backend osrm-routed
--algorithm mld --max-table-size 2000 /data/msk.osrm`, так же `osrm-bike` (порт 5002, папка `bicycle`) и `osrm-foot`
(5001, `foot`). Адреса серверов задаются переменными `OSRM_CAR`, `OSRM_BIKE`, `OSRM_FOOT`.

## Структура

| Папка | Что внутри |
|---|---|
| `dispatch/` | Продукт на Python: `files/` — чтение входа, `plan.json`, xlsx и сводки; `geo/` — геокодинг, OSRM, матрицы, линии маршрутов; `model/` — заявки, бригады, задача и расписание; `solve/` — запуск решателей; `planning/` — план, проверка, объяснения, перепланирование; `site/` — страница диспетчера; `tools/` — подготовка данных |
| `solver/` | Решатели продукта на C++: `plan` (кооперативный поиск), `baseline` (жадный вариант из ТЗ), `fleet_bound` (нижняя граница числа бригад); вход и выход — `docs/SOLVER_IO.md` |
| `tests/` | `unit/` — модульные тесты на маленьких задачах, `e2e/` — сквозные тесты команд на демо-данных |
| `cache/` | Координаты адресов, матрицы OSRM, линии маршрутов |
| `data/` | `organizers/` — данные и ТЗ организаторов, `demo/` — входные файлы для демо, `generated/` — сгенерированные участки |
| `docs/` | Решение (`SOLUTION.md`), контракт с решателями (`SOLVER_IO.md`), допущения, вопросы и ответы жюри (`qa.txt`) |
| `presentation/` | Презентация и скрипты её сборки |
| `research/` | Эксперименты: все решатели, точные методы, бенчмарки, макеты интерфейса |
| `osrm/` | Графы OSRM: скачиваются `osrm/download.sh` или собираются `osrm/build.sh` |
| `scripts/` | `demo.sh` — демо целиком |
