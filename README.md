# Пульс — планирование выездов инженеров (команда Трдельник)

По заявкам дня и составу бригад строим план:
какая бригада какие заявки выполняет, в каком порядке и во сколько; перестраиваем его после событий в течение дня и
показываем диспетчеру на карте с объяснениями.

- **Демо без установки:** https://route-dispatcher-trdelnik.vercel.app
- Модель, алгоритм, точные методы и результаты — [docs/SOLUTION.md](docs/SOLUTION.md)
- Допущения и ответы жюри — [docs/assumptions.md](docs/assumptions.md), стенограмма вопросов и ответов — [docs/qa.txt](docs/qa.txt)
- Контракт с решателями на C++ — [docs/SOLVER_IO.md](docs/SOLVER_IO.md)
- Презентация — [presentation/presentation_trdelnik.pdf](presentation/presentation_trdelnik.pdf)

## Запуск одной командой

Нужен Docker.

```
docker compose up --build
```

Откройте http://localhost:8080. Контейнер собирает решатели, строит планы шести участков (Восток, Югоцентр,
Юго-восток, Север, Запад, Северо-восток) и варианты Востока (лучшие монтажники, смены 5/2, по историческим данным —
истории выездов), перестраивает план Востока после событий дня и запускает страницу диспетчера. Первый запуск — около 17 минут: из них
около 3 минут — Юго-восток (3 запуска решателя по 30 с против сохранённого лучшего ответа) и около 6 — Восток 5/2
(5 по 60 с).
Заявки и бригады для событий «недоступна», «отмена», «закончили позже», «перенос окна» и «поломка» выбирает по свежему
плану `scripts/demo_events.py`. Разворот бригады в пути к аварии подбирается по домам OSM из `data/osm/` — их нет ни
в git, ни в контейнере, и без них этого сценария на странице не будет.

Расписания общественного транспорта (`data/transit/`, не в git) и сетка пробок HERE в контейнере те же, что у нас:
время на общественном транспорте уже лежит в `cache/matrix_pt.json`, сетка — в `data/traffic/`.

OSRM для демо не нужен: координаты, матрицы времени и расстояний и линии маршрутов по улицам лежат в `cache/`, и
готовые сценарии страницы работают без него. Решатель многопоточный, и план от запуска к запуску немного разный:
переезды, которых нет в кэше линий, без OSRM рисуются прямыми, а карта аварийного покрытия без OSRM не строится.
OSRM нужен, чтобы считать новые точки: свои адреса в `plan` и `replan` и страницу со своими событиями (`site --api`,
см. «Свои события на странице»). Без своего OSRM свои события доступны только в уже выложенной версии с сервером
пересчёта (`scripts/build_vercel.sh`, раздел «Страница на Vercel»).
Браузеру нужен интернет: подложка карты OpenStreetMap, библиотека Leaflet и шрифты грузятся из сети. Для новых
адресов — см. «Новые адреса: геокодинг и OSRM».

## Без Docker

Нужны clang или g++, make, Python 3.11+.

```
make -C solver                                             # решатели: solver/bin/plan, baseline, fleet_bound, fleet_proof, transit
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
scripts/demo.sh                                            # то же, что контейнер; --no-serve — без запуска страницы
```

`scripts/demo.sh` пишет результаты в `out/<участок>/`, страницу — в `site/` и открывает её на порту `PORT`
(по умолчанию 8080). Восток — лучший из 5 запусков решателя по 10 секунд, Юго-восток — лучший из 3 запусков по 30 секунд и
сохранённого лучшего ответа `data/demo/Юго-восток_ответ.json` (`plan --answer`), Восток 5/2 — из 5 по 60 секунд,
остальные участки — один запуск на 3 секунды. Страница — по сценариям: список слева
вверху, группы по требованиям второго этапа; экран инженера — `engineer.html` (ссылка «Экран инженера» в шапке).

## Сценарий демо (раздел 4 ТЗ)

| Шаг ТЗ | Где на странице |
|---|---|
| 1–2. Открыть данные, запустить планирование | `python -m dispatch plan …` (или `scripts/demo.sh`); на странице — список «Сценарий» слева вверху (группа «Планы участков») |
| 3. Распределение и маршруты на карте | карта, бригады в работе, диаграмма дня; под картой — шкала времени с кнопкой «Пуск» |
| 4. Почему заявка назначена этой бригаде | клик по точке на карте или по блоку на шкале — карточка заявки с объяснением |
| 5–6. Событие и перестроенный план | сценарий с событием: отметка на шкале времени; до неё — утренний план, после — пересчитанный: что изменилось, было / стало, новые участки маршрутов |
| 7. Сравнение с базовым вариантом | метрики вверху и блок «Сравнение с базовым вариантом»: бригады, пробег по каждой бригаде и всего |

Готовые события Востока на странице: авария в 14:00, разворот бригады в пути к аварии (если есть `data/osm/`),
новое подключение в 13:30, отмена заявки в 13:00, клиент перенёс окно в 13:00, сломалась машина в 13:00, работа
затянулась (12:30), Бригада 4 недоступна с 14:00. Любое другое событие — командой `replan` (ниже) или кнопкой
«＋ Событие» на странице с сервером пересчёта (`site --api`, `serve`).

### Свои события на странице

```
python -m dispatch site out/Восток -o site --api      # нужен запущенный OSRM
python -m dispatch serve site
```

`site --api` кладёт в `site/api/<участок>/` пакеты данных для сервера пересчёта (`dispatch/api.py`): пары точек дня из
кэша и сетку точек с шагом 500 м вокруг них — сетку считает OSRM, поэтому без него пакеты не собрать. Самому серверу
(`serve`, если в папке есть `api/`) OSRM уже не нужен: время до новой точки (клик по карте, точка разворота) он
оценивает через ближайшие точки сетки. Запросы страницы к серверу:

| Запрос | Что делает |
|---|---|
| `POST /api/variants` | событие → три варианта ответа (`insert`, `optimize`, `keep`, как `replan --strategy`) с новыми планами |
| `POST /api/options` | какие бригады могут взять заявку: прирост км, сколько визитов сдвинется, почему нельзя |
| `POST /api/move` | передать заявку другой бригаде (перетаскивание на диаграмме) → новый план |

Состояния у сервера нет: страница присылает текущий план и событие, сервер возвращает новый план.

## Команды

Из корня проекта: `python -m dispatch <команда>` (в `.venv`: `.venv/bin/python -m dispatch …`).

| Команда | Что делает |
|---|---|
| `plan <заявки> -b <бригады> -o <папка>` | План на день: наш решатель, базовый вариант из ТЗ, нижняя граница числа бригад, проверка, причины неназначения и объяснения |
| `replan <папка плана> --at 14:00 <событие> -o <папка>` | Перестройка после события |
| `site <папки> -o site [--api] [--scenarios scripts/scenarios.json]` | Страница диспетчера по результатам `plan` и `replan`: каждое событие привязывается к плану, от которого сделан `replan` |
| `serve [site] [--port 8080]` | Открыть страницу локально |
| `prefetch <папки плана>` | Линии по улицам для всех пар точек участка в кэш, чтобы показывать без OSRM |
| `demo-data [--transport mix1\|mix2\|pt\|car]` | Файлы бригад и заявок для демо по данным организаторов → `data/demo/` |
| `gen-district Север Запад Северо-восток [--seed 1]` | Новые участки Москвы с настоящими адресами из OpenStreetMap; при первом запуске режет `osrm/msk.osm.pbf` в `data/osm/` программой `osmium` (системный пакет `osmium-tool`) |
| `reviews [участки]` | Синтетика для рейтинга: парк из 30 монтажников и история отзывов клиентов за 60 дней |
| `homes [участки]` | Дома бригад для демо: старт рабочего дня из дома (настоящие жилые дома OSM) |
| `houses [файлы заявок] [--osm …]` | Данные о домах для коэффициента сложности (подъезд, этаж, лифт, шлагбаум, офис) → `cache/houses.json` |
| `calibrate sample\|fit <файл> [-n 30] [--apikey …]` | Калибровка коэффициента пробок по Яндекс Картам |
| `facts` | Синтетика для режима «по историческим данным» (истории выездов; в справке команды — «план учится»): история фактических длительностей выездов → `data/demo/выезды.csv` |
| `transit` | Сеть общественного транспорта по расписаниям из `data/transit/` (GTFS Мосгортранса, схема Мосметро, сохранённые ответы Яндекс Расписаний, автобусы области из OSM) → `data/transit/net` |

Данные для `transit` (папка `data/transit/`, в git не входит):

```
mkdir -p data/transit/gtfs data/transit/metro
curl -L -o data/transit/gtfs/latest.zip https://files.mobilitydatabase.org/mdb-3226/latest.zip     # GTFS Мосгортранса
curl -L -o data/transit/metro/schema.json https://prodapp.mosmetro.ru/api/schema/v1.0              # схема Мосметро

.venv/bin/python -m dispatch transit       # автобусы области — из osrm/cfd.osm.pbf, если он есть
```

Параметры `plan`:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `--name` | из имени файла | название участка |
| `--time` | 3 | время решателя, секунды |
| `--seed` | 1 | сид решателя |
| `--tries` | 1 | запусков решателя с сидами seed, seed+1, …; берётся лучший план: меньше невыполненных, затем бригад, затем км + 0,1 км за минуту ожидания аварий |
| `--answer` | — | ответ решателя прошлого прогона (`answer.json`) на те же файлы: соревнуется с новыми запусками; с `--tries 0` — только он |
| `--traffic` | `car=1.3` | множитель времени OSRM по видам транспорта |
| `--overhead` | `car=5,pt=3,bike=3,foot=3` | минуты на подход к заявке: парковка, дверь, домофон |
| `--no-geometry` | — | не строить линии маршрутов по улицам (быстрее, без OSRM и кэша линий) |
| `--schedule` | из файла бригад | график бригад без колонки «График»: `2/2` — 10:00–22:00, `5/2` — по очереди 10:00–19:00 и 13:00–22:00 |
| `--flat-traffic` | — | пробки одним коэффициентом на весь день, без поправки на час окна и район |
| `--facts` | — | история фактических длительностей выездов (CSV): коэффициенты сложности уточняются по ней |
| `--no-lunch` | — | без обеда (по умолчанию 45 мин, начало с 13:00 до 15:15, у смен от 6 ч) |
| `--no-equipment` | — | без учёта оборудования (роутеры, приставки; пешком и на общ. транспорте — до 2 единиц) |
| `--curve` | — | кривая «бригады против км»: план с пределом бригад от минимума −3 до +3 |
| `--price` | — | цена ограничений: план без одного правила за раз, с доказанной нижней границей |
| `--coverage` | — | карта аварийного покрытия: через сколько минут начнут аварию в каждой точке участка (нужен OSRM) |
| `--deficit` | — | свободные окна «районы × окна»: сколько ещё подключений помещается |
| `--early` | — | что если клиенты согласятся начать до часа раньше окна: бригады, км и кому звонить |
| `--windows` | — | цена точного времени: часовые окна вместо двухчасовых у 25/50/100% клиентов |
| `--reviews` | — | отзывы клиентов (CSV, `reviews`): рейтинги монтажников в плане |
| `--best` | — | режим «лучшие»: наименьшее K лучших по рейтингу, которые закрывают день, и цена качества (нужен `--reviews`) |

`--tries` действует только на основной план. Расчёты «что если» (`--curve`, `--price`, `--best`) и план по нормативам
без коэффициента сложности — по одному запуску решателя на каждый вариант с тем же `--time` и `--seed`, поэтому их км
могут немного отличаться от основного плана. У `--early` и `--windows` из подходящих планов берётся лучший: основной
план годится и для раннего старта, и для 0% «точного времени», а план с более узкими окнами — и для более широких.
Поэтому 0% совпадает с основным планом, а ранний старт, который ничего не даёт, помечен `useful: false`.

`--answer FILE` — ответ решателя прошлого прогона на те же файлы (`answer.json` из папки результата): он соревнуется
с новыми запусками, берётся лучший; с `--tries 0` решатель не запускается. Ответ проверяется по расписанию: если входные
файлы или матрицы с тех пор поменялись и он стал недопустим, он пропускается (с `--tries 0` — ошибка). Демо так держит
лучший известный план Юго-востока: `data/demo/Юго-восток_ответ.json`.

События `replan` (одно на запуск): `--unavailable "Бригада 4"` (имя или номер), `--cancel <номер заявки>`,
`--finish <номер заявки> 14:00` (работа закончилась или закончится в это время — раньше или позже плана),
`--reschedule <номер заявки> 16:00-18:00` (клиент перенёс окно), `--breakdown "Бригада 1" [--to pt|foot|bike]`
(сломалась машина — бригада продолжает день на другом транспорте) или
`--urgent "<адрес>"` / `--urgent "55.74, 37.72"` с `--type авария|подключение|ремонт|дозаказ` (по умолчанию авария),
`--window 15:00-17:00`, `--need авто`, `--id <номер>`, `--district <район>`. У аварии окно не нужно: она должна
начаться не позже чем через 2 часа.

Как перестраивать — `replan --strategy`: `insert` (по умолчанию) — минимум перестановок по правилам ниже; `optimize` —
лучший план на остаток дня решателем, время решателя — `replan --time` (по умолчанию 3 с); `keep` — ничего не менять:
новые и снятые заявки остаются без исполнителя. На странице с сервером пересчёта это три варианта ответа на событие.

```
python -m dispatch plan "data/demo/Восток заявки.xlsx" --name Восток -b "data/demo/Восток бригады.xlsx" -o out/Восток
python -m dispatch replan out/Восток --at 14:00 --urgent "55.74, 37.72" --type авария -o out/Восток_авария
python -m dispatch site out/Восток out/Восток_авария -o site
python -m dispatch serve
```

## Входные данные

Примеры — `data/demo/`. Исходные файлы организаторов — `data/organizers/`.

**Заявки** — CSV организаторов (CP1251 или UTF-8, разделитель «;») или xlsx с теми же колонками. Строка заголовка
начинается с «Заявка».

| Колонка | Значение |
|---|---|
| Заявка | номер |
| Тип заявки BK | `Подключение`, `Глобальная проблема` (авария), `Локальная заявка` (ремонт), `Дозаказ` |
| Тип заявки HD | подтип, только для показа (необязательная) |
| Начало, Окончание | окно начала работ: `17.08.2026 12:00` или `12:00` |
| Район, Адрес | адрес в формате организаторов |
| Транспорт | необязательная: требуемый транспорт — `авто`, `авто или велосипед`; пусто или `любой` — без ограничения |

Последняя строка — `Адрес офиса; <адрес>`: оттуда выезжают бригады без своего старта.

**Бригады** — xlsx или CSV: `Бригада; Транспорт; Навыки; Старт`. Транспорт — `авто`, `общ. транспорт`, `велосипед`,
`пешком`. Навыки через запятую — `ремонт`, `подключение` (подключение и дозаказ), `аварии`. Старт — пусто (офис),
адрес или `широта, долгота`. Необязательные колонки: «График» (`2/2`, `5/2`), «Смена» (`13-22`), «Оборудование»
(`роутер 4, приставка 2` — запас на день; без неё — нужное маршруту и по одной запасной), «Уровень» (`стажёр` ×1,15,
`инженер` ×1,0, `старший` ×0,9 к длительности работ), «Темп» (свой множитель, важнее уровня).

**Справочники ТЗ (2.4.1) → наши значения.** Навыки: 1 «Локальные работы» → ремонт, 2 «Подключение и дозаказы» →
подключение, 3 «Аварийные работы» → аварии. Транспорт: 1 автомобиль → авто, 2 пешеход → пешком, 3 велосипед,
4 общественный транспорт. Приоритет задаётся типом заявки: авария → подключение → ремонт и дозаказ; срочная
заявка приходит событием `replan --urgent`.

**Нормативы и единицы.** Работа на месте: подключение 70 мин, авария 80, ремонт 30, дозаказ 20 (Нормативы.xlsx без
20 минут «дороги» — дорогу считаем по картам). Смена по умолчанию 10:00–22:00 (график 2/2); при графике 5/2 —
10:00–19:00 или 13:00–22:00 (колонки «График» и «Смена» в файле бригад или `plan --schedule 5/2`). Работа должна
начаться внутри окна и закончиться до конца смены; приехать раньше и ждать можно. Время — ЧЧ:ММ, длительности и время в пути — минуты,
расстояния — км, координаты — широта/долгота.

## Результат

`plan` пишет в папку результата:

| Файл | Что внутри |
|---|---|
| `plan.xlsx` | листы «Маршруты» (бригада, порядок, заявка, адрес, окно, приезд, начало, конец, км от предыдущей), «Бригады», «Метрики», «Неназначенные» с причиной, «Объяснения», «Базовый вариант», «Базовый — неназначенные»; после `replan` ещё «Изменения» |
| `plan.json` | всё то же для страницы: заявки, бригады, маршруты с временем и км, метрики, проверка, причины, объяснения, базовый вариант, нижняя граница; после `replan` — событие и список изменений |
| `task.txt`, `answer.json` | задача и ответ решателя — их можно проверить независимо (формат — `docs/SOLVER_IO.md`) |

Метрики из ТЗ: число задействованных бригад, пробег по каждой бригаде и суммарный — у нашего плана и у базового
варианта. Каждый план проходит отдельную проверку всех ограничений (`dispatch/planning/validate.py`): навык,
окно, смена бригады, требуемый транспорт, обед, оборудование и сколько бригада унесёт, каждая заявка назначена не
больше одного раза; после события — что выполненное и начатое не изменилось.

## Как считаем

- **Цель по порядку важности:** выполнить все заявки (если нельзя — сначала аварии, затем подключения, затем
  остальные), затем меньше бригад, затем меньше километров плюс 0,1 км за каждую минуту от начала окна аварии до
  начала работ (`config.WAIT_KM_PER_MIN`, параметр `wwait` решателя) — так аварии начинаются раньше.
- **Время в пути:** OSRM по дорогам OpenStreetMap; машина × 1,3 (пробки, сверено по Яндекс Картам) с поправкой на
  час окна заявки, день недели и место (сетка HERE ~330 м, без неё — четыре района) + 5 мин на подход, остальные + 3 мин.
  Общественный транспорт — по расписаниям (метро, МЦК, МЦД, электрички, автобусы и трамваи Москвы, автобусы области),
  среднее время с ожиданием в часы окна заявки; если пешком быстрее — пешком. Если по расписанию не доехать — только
  пешком; оценка по расстоянию — только когда расписания нет (сеть не собрана, `python -m dispatch transit`): до 1,5 км
  пешком, дальше 12 мин на подход и ожидание и 20 км/ч, после 25 км — 45 км/ч. Подробно — `docs/SOLUTION.md`, 9.9.
- **Решатель** (`solver/bin/plan`, исходники — `solver/src/`, C++): потоки с разными эвристиками (имитация отжига,
  ALNS, SISR; сколько и какие — по числу ядер) обмениваются лучшим планом. **Базовый вариант** (`solver/bin/baseline`) —
  ровно правило раздела 2.3 ТЗ. **Нижняя граница** (`solver/bin/fleet_bound`) — генерация столбцов: доказывает, меньше
  какого числа бригад нельзя. В демо минимум бригад доказан на всех шести участках и на Востоке 5/2.
- **Результаты в модели первого этапа** (смена 10–22 без обеда, транспорт по средней скорости, пробки одним
  коэффициентом): на 88 тестовых задачах план во всех выходит на доказанный минимум бригад; у базового варианта
  бригад на 41% больше и 22% заявок не выполнено. Подробно — [docs/SOLUTION.md](docs/SOLUTION.md), раздел 6.
- **Те же 88 задач в текущей модели** (обед, оборудование, старт из дома, длительность по сложности, общественный
  транспорт по расписаниям, пробки по часам и районам) — `research/deck_report_v2.md`: у базового варианта бригад на
  22% больше и 32% заявок не выполнено; план за 3 с на доказанном минимуме штрафа и бригад в 70 из 88 задач. Граница
  там считалась с прежней памятью ng = 8 (продукт теперь передаёт `fleet_bound` ng = 24), поэтому это число, скорее
  всего, занижено.

### Правила перепланирования

Выполненное и начатое к моменту события не меняется. Новая обычная заявка встаёт в свободный промежуток, порядок
остальных не меняется. Авария, появившаяся в течение дня, начинается как можно раньше и не позже чем через 2 часа:
в цене каждая минута ожидания аварии, каждый перенос заявки и вывод резервной бригады. Заявки недоступного инженера
переходят к другим бригадам, затем к резерву. Отмена освобождает время для неназначенных заявок.

## Новые адреса: геокодинг и OSRM

Новые адреса переводятся в координаты через Nominatim (нужен интернет, не чаще раза в секунду) и сохраняются в
`cache/geocode.json`. Время и расстояние для новых точек даёт только свой OSRM:

```
osrm/download.sh                        # готовые графы из релиза GitHub: 1,2 ГБ, распакованные ~3 ГБ
docker compose --profile osrm up        # приложение и три сервера OSRM
```

`download.sh` качает через `gh`, пока репозиторий приватный (нужен `gh auth login` с доступом к нему), иначе через
`curl`. Собрать графы самим из OpenStreetMap: `osrm/build.sh` (Docker, ~8 ГБ памяти, 15–30 минут).

Без Compose: `docker run -d --name osrm-car -p 5003:5000 -v $PWD/osrm/car:/data osrm/osrm-backend osrm-routed
--algorithm mld --max-table-size 2000 /data/msk.osrm`, так же `osrm-bike` (порт 5002, папка `bicycle`) и `osrm-foot`
(5001, `foot`).

## Страница на Vercel

Проект `route-dispatcher-trdelnik`. Статическая страница (без пересчёта событий на сервере): `cd site && vercel
deploy --prod`; если папка пересоздана, сначала `vercel link --project route-dispatcher-trdelnik`. Со своими
событиями и передачей заявок: `scripts/build_vercel.sh` собирает папку `vercel/` (страница с `--api`, сервер
`dispatch/api.py`, решатели под Linux) — затем `cd vercel && vercel deploy --prod`.

## Тесты

```
.venv/bin/python -m pytest                 # всё, ~3 мин (страница в браузере — если установлен playwright)
.venv/bin/python -m pytest -m "not e2e"    # только модульные
```

Модульные — на маленьких задачах «на прямой», где расписание считается в уме; OSRM и сеть им не нужны. Часть из них
запускает настоящие решатели из `solver/bin` (`tests/unit/test_gaps_cli.py`, сеть общественного транспорта в
`test_transit_net.py`) и без собранных решателей пропускается. Сквозные (`tests/e2e/`) запускают настоящие решатели
на демо-данных Востока без OSRM: план, отчёт xlsx, события, страницу, сообщение об ошибке во входном файле, контракт
с решателями. Им нужны собранные решатели (`make -C solver`) и кэши в `cache/`.

## Ограничения и что дальше

- От длины смены во многом зависит экономия бригад (Восток: 2/2 — 8 бригад, 5/2 — все 12 и две заявки не помещаются).
- Оборудование у клиента — синтетика (жюри разрешило): роутер у половины подключений, приставка у части; пополнения
  запаса в течение дня и передачи между бригадами нет.
- Общественный транспорт — по расписанию GTFS Мосгортранса (май 2025), схеме Мосметро и расписанию Яндекса для МЦД и
  электричек (один будний день, пять направлений вне МЦД). Автобусы области — маршруты OpenStreetMap с интервалом по
  правилу (15 мин в городе, 45 — пригородные), настоящего расписания области в открытом доступе нет.
- Пробки — профиль города по часам и дням недели (TomTom, 2021) и сетка ~330 м по зондам HERE 2018 (13 будних дней);
  направление движения данные не различают, доля поездки считается по прямой, а не по маршруту.
- Строгий порядок «сначала бригады, потом км» иногда даёт дорогой размен (одна бригада против сотни км); кривая
  «бригады против км» (`plan --curve`) показывает его, но выбор точки на кривой пока не в интерфейсе.
- Дальше: планирование на несколько дней, пополнение оборудования в течение дня, точное время общественного
  транспорта на момент выезда (сейчас — среднее за часы окна).

Подробно — [docs/SOLUTION.md](docs/SOLUTION.md), раздел 8.
